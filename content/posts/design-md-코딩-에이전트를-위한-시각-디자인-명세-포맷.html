DESIGN.md - 코딩 에이전트를 위한 시각 디자인 명세 포맷

Source: https://github.com/google-labs-code/design.md

Summary

google-labs-code/design.md는 코딩 에이전트가 일관된 시각 정체성을 이해하고 구현할 수 있도록 만든 디자인 시스템용 텍스트 명세 포맷 저장소다.
핵심 아이디어는 DESIGN.md 파일 안에 YAML front matter 기반의 machine-readable design tokens와 Markdown 기반의 human-readable design rationale를 함께 담아, 에이전트가 “값”과 “의도”를 동시에 읽도록 만드는 것이다.
저장소는 포맷 개요뿐 아니라 lint, diff, export, spec 같은 CLI 흐름도 제공해서, 단순 문서 규약이 아니라 검증·비교·변환 가능한 디자인 명세 체계로 설계되어 있다.
즉 이 프로젝트는 프롬프트에 산발적으로 디자인 지시를 적는 대신, 디자인 시스템을 별도 문서로 고정해 여러 AI 에이전트와 도구 사이에서 재사용하려는 시도라고 볼 수 있다.

핵심 포인트

  • DESIGN.md는 디자인 토큰과 디자인 설명문을 한 파일에 함께 담는 포맷이다.
  • YAML front matter는 에이전트가 바로 읽을 수 있는 정규값을 제공하고, Markdown 본문은 그 값을 왜/how 쓰는지 설명한다.
  • 명세는 색상, 타이포그래피, spacing, rounded, component token reference 같은 구조를 정의한다.
  • 섹션 순서와 토큰 타입, unknown content 처리 방식까지 정리되어 있어 포맷 안정성을 높인다.
  • CLI는 lint/diff/export/spec 워크플로를 제공해 실제 팀 운영에 붙이기 쉽다.
  • 결과적으로 디자인 시스템을 “에이전트가 읽는 계약서”처럼 만들려는 프로젝트다.

Clipped Content

이 프로젝트가 해결하려는 문제

README의 첫 문장은 DESIGN.md를 “coding agents에게 visual identity를 설명하기 위한 포맷 명세”라고 정의한다. 즉 목표는 사람이 Figma나 감각적인 설명으로만 공유하던 디자인 시스템을, AI가 재사용 가능한 형태로 고정하는 것이다.

이 접근의 포인트는 두 층을 분리하지 않고 한 문서에 함께 둔다는 점이다.

  1. YAML front matter
    • 색상, 타이포그래피, spacing, radius 같은 토큰을 기계가 읽기 좋은 구조로 담는다.
  2. Markdown body
    • 브랜드 성격, 시각적 분위기, 사용 의도, 적용 원칙을 사람이 읽기 좋은 prose로 적는다.

문서가 강조하는 메시지는 분명하다. 토큰은 exact values를 주고, prose는 그 값이 왜 존재하며 어떻게 써야 하는지를 알려준다. 즉 단순 스타일 가이드가 아니라, 에이전트가 일관된 UI를 생성하기 위한 컨텍스트 문서다.

README 예시가 보여주는 형태

README는 Heritage라는 예시를 통해 다음과 같은 구조를 보여준다.

  • colors.primary, colors.secondary, colors.tertiary, colors.neutral
  • typography.h1, typography.body-md, typography.label-caps
  • rounded.sm, rounded.md
  • spacing.sm, spacing.md

이후 prose 섹션에서는 “Architectural Minimalism meets Journalistic Gravitas” 같은 식으로 브랜드 톤을 설명하고, 색상이 어떤 역할을 맡는지도 자연어로 풀어준다. 이 예시는 DESIGN.md가 단순 token dump가 아니라, 값 + 해석 + 스타일 의도를 함께 전달하는 포맷이라는 점을 잘 보여준다.

포맷 구조

명세 문서(docs/spec.md) 기준으로 DESIGN.md는 self-contained plain-text design system 표현이다. 구조적으로는 다음 두 부분을 가진다.

  • Optional YAML front matter: machine-readable design tokens
  • Markdown body: human-readable design rationale and guidance

토큰은 normative values이고, prose는 application context를 준다. 명세는 토큰 시스템이 Design Token JSON spec의 typed token groups와 {path.to.token} reference 문법에서 영감을 받았다고 설명한다.

토큰 스키마와 타입

README/스펙을 합치면 핵심 스키마는 대략 이렇다.

version: <string>
name: <string>
description: <string>
colors:
  <token-name>: <Color>
typography:
  <token-name>: <Typography>
rounded:
  <scale-level>: <Dimension>
spacing:
  <scale-level>: <Dimension | number>
components:
  <component-name>:
    <token-name>: <string | token reference>

중요 타입은 다음과 같다.

  • Color: #로 시작하는 hex sRGB 값
  • Dimension: px, em, rem 단위를 갖는 문자열
  • Token Reference: {path.to.token} 같은 cross-reference 문법
  • Typography: fontFamily, fontSize, fontWeight, lineHeight, letterSpacing 등을 가진 객체

이 구조는 나중에 tokens.json, Figma variables, Tailwind theme 등으로도 변환하기 쉽게 설계되어 있다.

섹션 순서 규약

스펙은 ## heading 기준 섹션 순서도 정한다. 필요한 섹션만 써도 되지만, 존재하는 섹션은 아래 순서를 따르는 것이 권장된다.

  1. Overview
  2. Colors
  3. Typography
  4. Layout
  5. Elevation and Depth
  6. Shapes
  7. Components
  8. Do's and Don'ts

즉 자유 서술형 문서처럼 보이지만, 실제로는 에이전트가 예측 가능하게 읽을 수 있도록 구조화된 문서 질서를 부여한 포맷이다.

컴포넌트 토큰과 reference

README는 components.button-primary.backgroundColor: "{colors.tertiary}" 같은 식의 component-level mapping 예시도 보여준다.

여기서 중요한 점은 DESIGN.md가 단순 글로벌 token만 보관하는 것이 아니라, 버튼/hover 상태 등 UI component 수준의 의미 있는 매핑도 담는다는 점이다. 그래서 에이전트는 단순히 “주색은 무엇인가?”가 아니라, “기본 버튼 배경색은 어떤 토큰을 참조해야 하는가?”까지 추론할 수 있다.

Unknown content 처리 원칙

README condensed reference는 unknown section heading, unknown token name, unknown component property, duplicate heading에 대한 consumer behavior도 표로 설명한다.

핵심은 대체로 다음과 같다.

  • 모르는 섹션/토큰 이름은 가능한 한 보존/허용한다.
  • 다만 unknown component property는 warning 대상이 될 수 있다.
  • duplicate section heading은 error로 reject한다.

이 철학은 포맷을 너무 엄격하게 닫아버리기보다, 확장 가능성은 열어두고 깨질 만한 구조만 엄격히 잡는 방향에 가깝다.

CLI 워크플로

README에서 실용적으로 가장 중요한 부분은 CLI다.

1) lint

npx @google/design.md lint DESIGN.md
  • 구조 오류 검증
  • broken token reference 탐지
  • WCAG contrast ratio 점검
  • structured JSON 결과 출력

즉 DESIGN.md를 그냥 작성만 하는 것이 아니라, 에이전트나 CI가 검증 가능한 산출물로 다룬다.

2) diff

npx @google/design.md diff DESIGN.md DESIGN-v2.md
  • 두 버전 간 token-level 변화 확인
  • prose regression 감지
  • 회귀 여부를 exit code와 JSON으로 표현

이 기능은 디자인 시스템의 변화를 코드 diff처럼 추적하려는 발상이라서 특히 흥미롭다.

3) export

npx @google/design.md export --format tailwind DESIGN.md
npx @google/design.md export --format dtcg DESIGN.md
  • Tailwind theme
  • DTCG 스타일 토큰 포맷

등으로 내보낼 수 있어, DESIGN.md를 단순 문서가 아니라 변환 허브처럼 사용할 수 있다.

4) spec

npx @google/design.md spec

활성 규칙표나 rules-only JSON까지 뽑을 수 있어서, 에이전트 프롬프트나 검증 파이프라인에 명세를 그대로 주입하는 용도로도 쓸 수 있다.

왜 의미 있는가

이 저장소가 흥미로운 이유는 디자인 시스템을 “디자이너용 문서”에서 “에이전트와 개발도구가 함께 읽는 인터페이스”로 바꾸려 한다는 점이다.

기존에는:

  • Figma 변수
  • 별도 디자인 가이드
  • 코드 안의 theme 파일
  • 프롬프트 안의 스타일 지시

가 여러 군데 흩어져 있었다면, DESIGN.md는 이를 한 문서로 묶어 single source of truth에 가깝게 만들려는 시도다.

특히 여러 에이전트가 협업하는 환경에서는 “이 프로젝트의 시각적 정체성”을 매번 프롬프트로 다시 설명하지 않고, DESIGN.md를 참조하게 하는 방식이 꽤 실용적으로 보인다.

짧은 해석

DESIGN.md는 AGENTS.md가 작업 규칙을 에이전트에게 넘기듯, 디자인 시스템의 시각 규칙을 에이전트에게 넘기는 대응물로 읽을 수 있다. 구현/디자인 협업을 텍스트 기반 계약으로 만들고 싶을 때 특히 참고 가치가 큰 저장소다.
